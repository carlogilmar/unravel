## Unravel App

The goal of this app is build a system to help developers to read, understand and correct code generated by AI. The speed of development with AI is incredible, but now we're generating more code than the code we can understand, so we're losing agency of knowledge.

Felienne Hermans explains how code is a cognitive activity that breaks into three parts: long-term memory, short-term memory and working memory. Code involve cognitive loads like understand the syntax, understand the logic abstraction and understand how the flow works. This parts are important to have agency and ownership of the code.

AI is powerful, but we need to develop context tools to help us to maintain the ownership.

## Technical Requirements

Unravel is a **terminal application (TUI)** written in **Go**, distributed as a single static binary. The inspiration is `lazygit`, `gh`, and `k9s` — tools that live next to the developer's existing workflow instead of opening a separate window.

**Stack**

- **Language:** Go (1.22+).
- **TUI framework:** [Bubble Tea](https://github.com/charmbracelet/bubbletea) (Elm-architecture), with [Lip Gloss](https://github.com/charmbracelet/lipgloss) for styling and [Bubbles](https://github.com/charmbracelet/bubbles) for reusable components (list, viewport, textinput).
- **Git:** [go-git](https://github.com/go-git/go-git) for in-process status and diff. Shell out to `git` only as a fallback where go-git is insufficient.
- **File watching:** [fsnotify](https://github.com/fsnotify/fsnotify) for the live editor loop (re-render when the working tree changes).
- **Syntax highlighting (v1.5+):** [chroma](https://github.com/alecthomas/chroma) — pure-Go, supports Elixir and Python.
- **Session storage:** SQLite via [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite) — pure-Go, no cgo. Global state in `~/.local/share/unravel/` (respecting `XDG_DATA_HOME`); per-project metadata optionally in `<project>/.unravel/`.

**Distribution**

- Single static binary, cross-platform (macOS, Linux, Windows).
- Installable via `brew install unravel`, `go install`, or a release tarball from GitHub, this for the future not for now.

**Why a terminal app instead of a desktop app**

The product thesis (see [REVIEW_CODE.md](./REVIEW_CODE.md)) is to *protect germane cognitive load*. A TUI's keyboard-driven, low-chrome environment is a better fit than a windowed app: the developer is already in "read and type" mode, not "click and skim" mode. It also ships as one static binary on every platform and lives next to the tools developers already use (`git`, `nvim`, `tmux`).

## Sprint 1 — "Read & Recognize" (MVP)

The point of Sprint 1 is a usable vertical slice: open a project → see what AI changed (assume everything in git working directory are AI changes) → read the diff with intent. Everything else waits.

### Core (must-have)

1. **Project entry** — Invoke `unravel` with no arguments to target `$PWD`, or `unravel <path>` to target a specific directory. Maintain a "recent projects" list (last 5) in `~/.local/share/unravel/recents.json`, navigable with `r` from the main screen. Validate the folder is a git repository on entry; surface a clear error otherwise.

2. **Git-aware change list** — Use `go-git` to enumerate working-tree changes vs. `HEAD`. Render a left-pane list grouped by status (Added / Modified / Deleted / Renamed). Filter to `.ex`, `.exs`, and `.py` for v1 — explicitly hide other extensions so the scope is honest.

3. **Diff viewer with "new code" highlighting** — Unified diff rendered in a right-pane viewport. Added lines styled distinctly from context lines via Lip Gloss. Line numbers from the new file. Syntax highlighting deferred to v1.5 — wiring chroma in is a one-evening task once the diff renderer is stable.

4. **Line-by-line reading mode** — Press `f` to enter focus mode. All lines except the current one dim to a low-contrast color; `j`/`k` (or `↑/↓`) advance one line at a time. This is the differentiator vs. a normal diff tool — it forces the cognitive pause Hermans describes, and the terminal's native modal feel reinforces the focus.

### Cognitive-load aids (the product thesis)

5. **"Mark as understood" per hunk** — Press `m` on a hunk to open the note prompt (a `bubbles/textinput`); the developer's answer to the modification test becomes the hunk's required "why" note. Persisted to SQLite, scoped by `(project, head_commit, file, hunk_id)`. A status-bar indicator shows "12/28 hunks understood." Marking is impossible without a note — the gesture must carry weight.

6. **Per-line notes** — Press `n` on any new line to attach a short note. Stored in SQLite, scoped to `(commit_SHA, file, line)`. These are the *externalized beacons* from REVIEW_CODE.md — durable across sessions and recallable on future visits to the same code.

### Foundation (invisible but required)

7. **Bubble Tea architecture** — Strict Elm-style separation: a single `Model`, pure `Update(msg) (Model, Cmd)` transitions, side-effects in `tea.Cmd`s. Define the core messages early: `LoadDiffMsg`, `MarkHunkMsg`, `SaveNoteMsg`, `FsEventMsg`. Get the model boundaries right in Sprint 1 or pay for it later.

8. **Empty and error states** — "Not a git repo", "No changes in working tree", "File too large to diff (>N lines)". Rendered as full-screen states, not toast popups — a TUI has no toast layer. Cheap to add now, painful to retrofit.

### Language scope for v1

Optimized for Elixir (`.ex`, `.exs`) and Python (`.py`). Other languages are listed in the change list only if explicitly enabled in settings; v1 ignores them by default.

### Explicitly deferred to Sprint 2+

- AI explanations of code (the obvious next feature, but Sprint 1 is about *human* reading).
- Staged vs. unstaged distinction.
- Branch comparison and arbitrary commit ranges.
- Syntax-aware highlighting and AST-level "new symbol" detection.
- Multi-language support beyond Elixir and Python.
- Cross-file flow visualization (working-memory aid).


### Use Case Scenarios

The flow below maps directly onto the cognitive practice developed in [REVIEW_CODE.md](./REVIEW_CODE.md). Each step exists because it protects *germane cognitive load* — the effortful learning that moves code from working memory into long-term memory. Steps that would feel like shortcuts (auto-summaries, one-click "looks good") are deliberately absent.

**Primary flow — a single review session**

1. A developer is working on a project and asks AI to generate or modify code.
2. AI writes the changes into the project (new files, new code, code removed). Nothing is committed yet — the working tree is dirty on purpose.
3. **Start the session — the hypothesis step.** The developer opens **Unravel** and points it at the project folder. The first prompt is a one-line text input: *"What do I think this change does?"* The answer becomes the session's hypothesis and pins to the top of the screen for the duration of the review. Writing it is the formal start of the session — there's no review state until the hypothesis is captured. Surprises against it later are the review signal worth chasing.
4. **Gist pass (top-down).** Unravel lists every file the AI touched, grouped by status (added / modified / deleted / renamed). The developer skims file names and change shapes — no bodies yet — to confirm or revise the hypothesis from step 3. If the working directory has no changes, the session ends immediately with a friendly message; there's nothing to review.
5. **Detail pass (bottom-up).** The developer picks a file and enters **reading mode**, advancing hunk by hunk. While reading, they hunt for *beacons* (Brooks 1983, Hermans Ch. 4) — names and structural choices that carry real meaning. Generic names like `data` or `result` are flagged as suspect; specific names like `unbilled_invoices` are treated as anchors.
6. **The modification test, not a checkbox.** Before marking a hunk ✓, the developer must be able to answer: *"Could I change this safely? Do I know its blast radius?"* The answer is captured as a short "why" note in the developer's own words — never the AI's. The note is an *externalized beacon*: a piece of long-term memory written down because the AI did not write it for them.
7. **Tests read separately from implementation.** AI-written tests often mirror the implementation rather than the spec, which creates an illusion of correctness when read together. The developer reads the test alone, predicts what the implementation should be, then checks. Mismatches are findings.
8. **Live editor loop.** If the developer spots something to fix, they switch to their code editor and edit normally. Unravel watches the working tree and re-renders the diff live — modified hunks reset to "unreviewed" because the code changed underneath them and the modification test must be re-passed.
9. **Close the session.** When every hunk has been marked understood with a "why" note attached, the developer presses `:close` (or `q` from the session-summary screen) to close the session. Unravel archives the session — files + hunks + notes + original hypothesis — keyed by the current `HEAD` SHA and a timestamp, so the externalized beacons can be recalled on future visits to this code. **What happens next is outside Unravel's scope**: the developer commits, opens a PR, pushes, shares, or walks away — whatever fits their workflow. Unravel's responsibility ends the moment the developer says they own the code.

**Secondary flows worth designing for in Sprint 1**

- **Mid-review AI iteration.** The developer asks AI for another round of changes halfway through the review. New hunks appear as "unreviewed"; previously-marked hunks stay marked *unless* their lines changed — in which case the modification test must be re-passed.
- **Resuming a paused review.** On reopen, Unravel restores the session: which hunks were marked, which notes were written, which file was last open, and the original hypothesis from step 3 — so the developer doesn't lose the thread.
- **Partial commit outside Unravel.** If the developer commits some files in their terminal mid-session, those files' working-tree diffs disappear. Unravel reflects this naturally — the committed files drop off the active list and the session continues with whatever's left. Unravel never asks "did you commit?" — it just watches the working tree.
- **Discarded changes.** If the developer reverts a file in their editor, the corresponding Unravel entries disappear silently. The source of truth is always the git working tree.
- **The "I don't understand this" hunk.** Marking a hunk ✗ is as important as ✓. An unresolved hunk blocks session close — the developer either learns it, edits it out, or closes the session with a known gap and a follow-up task. What is forbidden is closing the session while pretending to understand.

**Definition of "done" for a session**

A review session can be closed when, for every changed hunk:

1. The developer can pass the **modification test** (*"could I change this safely?"*),
2. A short "why" note exists, written by the developer in their own words, and
3. Tests have been read separately from the implementation they cover.

Only then can the developer close the session. Closing the session is the developer's own signal: *"I now own this code."* What happens to that code afterward — commit, push, open a PR, share, discard — is outside Unravel's scope. Unravel's job is to make the ownership statement honest, not to manage anyone's git workflow.

**What Unravel deliberately refuses to do** (drawn from REVIEW_CODE.md §6)

- **No AI-generated summaries of the diff.** Summaries reduce intrinsic cognitive load — they trade understanding for speed, which is the opposite of the product goal.
- **No auto-marking of "trivial" hunks.** Deciding what is trivial is itself the review.
- **No streaks, scores, or badges.** Marking a hunk understood should feel like signing one's name, not earning a point.

**Implication that resolves the earlier open question**

Sprint 1's "new code" target is unambiguously the **unstaged working-tree diff vs. `HEAD`** at the moment the session opens, re-evaluated live as the working tree changes. The "review cursor since last reviewed commit" idea moves to Sprint 2+, where it pairs naturally with a "last reviewed at" timestamp per file to surface ownership decay over weeks.
